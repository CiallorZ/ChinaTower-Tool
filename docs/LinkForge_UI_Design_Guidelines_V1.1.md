# LinkForge Windows 11 UI 设计规范与 Codex 实施准则
版本：V1.1  
适用产品：LinkForge 视联网全链路调试工具箱  
技术基线：C# / .NET / WPF / MVVM（沿用项目既定架构）  
目标读者：Codex、开发者、UI 实现与验收人员

---

## 0. 本文的执行优先级

本文是 UI 实现的强约束，不是灵感参考。开发时按以下优先级处理冲突：

1. 既有产品需求、功能安全边界与架构约束；
2. 本规范中的交互规则、信息架构、组件状态和验收条件；
3. 视觉细节与实现便利性。

**禁止**只做一张静态仪表盘、把所有页面做成同一种卡片堆叠、用假数据伪装已完成的功能，或只实现视觉而不实现加载/空/错误/成功等状态。所有页面应使用共享设计令牌与可复用组件。

## 1. 产品定位与体验目标

LinkForge 是面向工程师的 Windows 桌面诊断工作台，而不是营销型 SaaS 仪表盘。视觉上应现代、清晰、克制；使用上应可预测、可追踪、可恢复。

核心体验目标：
- **直觉**：常见任务在 1–2 个明确步骤内开始；重要动作有清晰动词和结果反馈。
- **高信息密度但不拥挤**：适合长时间使用；优先呈现状态、目标、结果和下一步。
- **一致**：同类操作在 RTSP、MQTT、HTTP、网络诊断等模块中采用相同模式。
- **可诊断**：任务必须显示目标、运行状态、耗时、结果、错误原因与可执行的下一步。
- **安全**：凭据默认遮蔽；扫描范围和潜在影响明确；破坏性操作需二次确认。
- **原生感**：遵循 Windows 11 Fluent Design 的层次、控件行为、键盘和窗口适配习惯，不模仿网页后台。

## 2. 视觉原则

### 2.1 视觉基调
- 主体使用浅色主题，提供完整深色主题；跟随系统主题作为默认设置。
- 背景以中性灰白为主，强调色用于主操作、选中状态和少量关键数据。
- 采用细边框、轻微层级差异和克制阴影；避免大面积渐变、玻璃拟态过度使用、霓虹色、厚重描边。
- 不把每个区域都装进卡片。页面优先用留白、分隔线、标题层级组织；只有需要聚合、对比或独立操作的内容才使用卡片。
- 图标优先使用一致的 Fluent/Segoe Fluent Icons 体系；禁止混用线性、填充、彩色 emoji 图标作为正式 UI 图标。

### 2.2 建议设计令牌（集中定义，不允许散落硬编码）

补充规则：
- 间距以 4px 为基础单位，常用 4/8/12/16/20/24/32px。
- 页面左右内边距常规 24px；密集表格页可 16–20px；弹窗内容 20–24px。
- 主文本通常 13–14px；页面标题 22–28px；区块标题 15–18px；辅助说明 12–13px。
- 最小可点击目标建议不低于 32×32px；高频操作优先 36px。
- 颜色不能作为唯一状态表达方式，必须配合文字、图标或状态标签。
- 深色主题需单独定义对应令牌，不可简单反色；对比度与焦点状态必须重新验收。

## 3. 应用窗口与全局布局

### 3.1 窗口结构
应用主窗口由四个稳定区域构成：
1. **应用标题栏/窗口控制区**：应用名称、全局搜索/命令入口（空间允许时）、最小化/最大化/关闭。
2. **主导航栏**：模块入口、当前项目/工作区上下文、底部设置与帮助入口。
3. **页面标题区**：页面名称、简短说明、面包屑（有层级时）、页面级主操作。
4. **内容工作区**：页面内容；必要时使用右侧详情栏或底部输出面板。

主布局建议：
- 左侧导航固定宽度约 240px，可折叠为图标模式；折叠后仍应提供 tooltip 和可访问名称。
- 主内容区随窗口缩放；禁止用固定绝对坐标构建整页。
- 常规页面在 1366×768 下应可完成核心任务；较小窗口允许纵向滚动，不得出现关键按钮被裁切。
- 任务输出/日志面板可停靠、折叠、调整高度；记住用户最后一次面板状态（若已有设置存储机制）。
- 使用 WPF Grid、DockPanel、ItemsControl 等布局容器与响应式行列，不以大量 Canvas/固定 Margin 模拟布局。

### 3.2 导航结构
推荐一级导航：
- 工作台
- 视频接入
- IoT 接入
- 网络诊断
- API 调试
- 安全检测
- 数据中心
- 常用工具
- 任务与报告
- 项目管理
- 设置

规则：
- 一级导航数量与名称以现有功能树为准；若仓库内已存在既定命名，不得擅自改名或删模块。
- 图标 + 文本同时呈现；当前项使用背景色/左侧指示线/文字权重体现选中，不只改变图标颜色。
- 有运行任务、失败任务或未读告警时，可显示轻量数字/状态提示，但不得让导航变成告警灯墙。
- 导航分组应按用户任务心智模型组织，不按底层类库或代码模块组织。
- 页面切换时保留可合理保留的上下文；切换模块不得意外取消正在运行的任务。

## 4. 信息架构与页面规范

### 4.1 工作台 Dashboard
目标：快速开始任务、查看近期项目与诊断健康状态，不做空洞的 KPI 装饰页。

推荐区域：
- 欢迎/当前工作区：当前项目名称、环境/配置上下文、切换项目入口。
- 快捷动作：新建诊断、RTSP 检测、HTTP 请求、MQTT 连接、网络路径检测等；仅显示实际已实现的动作。
- 最近项目/最近任务：名称、目标、最后运行时间、结果状态、继续/查看操作。
- 系统与任务状态：运行中任务、最近失败、设备连接摘要；没有真实数据时显示空状态，不编造数值。
- 常用工具入口：限制数量，允许用户配置或根据使用频率排序（若实现成本合理）。

布局规则：首屏优先呈现“开始工作”和“正在发生什么”；避免大面积欢迎横幅占据首屏；卡片内容要有可执行动作。

### 4.2 诊断工具统一页面模板
适用于 RTSP/ONVIF、MQTT、HTTP/API、TCP/UDP、DNS、Traceroute 等。

每个工具页统一包含：
1. 页面标题 + 一句话用途；
2. 目标/连接参数区域；
3. 可折叠的高级选项；
4. 明确的主操作（测试/连接/发送/开始扫描）；
5. 运行状态区；
6. 结构化结果区；
7. 原始输出/日志（可展开）；
8. 结果导出、复制或生成报告（按功能支持情况显示）。

执行流程统一为：**配置目标 → 校验输入 → 执行任务 → 展示过程 → 展示结论 → 提供下一步操作**。
- 输入校验应在启动前完成，并将错误放在字段附近。
- 运行中主按钮变为“停止”或禁用并明确说明，不允许用户误以为重复点击会启动第二个任务。
- 长任务显示已运行时间、阶段、取消入口；如果无法提供准确进度，使用阶段状态，不伪造百分比。
- 结果结论应先于原始日志；原始日志可查看但不应成为唯一输出。
- 错误结果必须包括可读原因、必要的错误码/原始信息和建议的下一步。
- 对相同协议工具复用同一套输入、状态、结果和日志组件。

### 4.3 视频接入 / RTSP / ONVIF
- 目标地址、协议/端口、用户名、密码分组清晰；密码默认遮蔽，提供显式显示开关。
- 支持的能力（如连通性、认证、RTSP 握手、媒体信息、ONVIF 发现）以步骤/检查项呈现。
- 结果显示每一步的状态、耗时、失败原因；避免只显示“成功/失败”。
- 若显示视频预览，应将预览作为可选区域，不得挤压关键诊断结果；没有实现解码时不能放置假视频占位冒充功能。
- 凭据、完整 RTSP URL 中的密码在日志、复制、导出报告中默认脱敏。

### 4.4 IoT 接入 / MQTT / Zigbee / HTTP
- MQTT 参数按 Broker、认证、TLS、客户端标识、订阅/发布分组；连接状态、重连状态、消息收发状态需明确。
- 消息列表采用表格/虚拟化列表，时间、Topic、QoS、方向、Payload 摘要清晰；长 Payload 在详情面板查看。
- Zigbee 等需要硬件或外部适配器的功能，明确区分“未连接”“驱动/适配器缺失”“功能尚未实现”。
- 不自动发布消息或写入设备；发送、控制、写操作要有明确的目标和动作文本。
- JSON/XML 等结构化内容提供格式化与校验；无效内容应保留原文并显示错误位置。

### 4.5 API 调试
- 请求方法、URL、参数、Header、认证、Body 使用清晰的标签页或分区；避免过度嵌套。
- 请求与响应并列或上下布局，应随窗口宽度调整；响应状态码、耗时、大小、Header、Body 分层展示。
- JSON 格式化、折叠节点、复制、保存样例等操作应在内容附近。
- 敏感 Header（Authorization、Cookie、API Key 等）在历史记录与导出中默认脱敏。
- 请求发送前显示可能影响状态的提示（例如 POST/PUT/PATCH/DELETE），但避免对每个只读 GET 请求反复弹窗。

### 4.6 网络诊断
- 统一呈现目标、检测类型、超时/次数等参数与“开始”操作。
- Ping、DNS、TCP 端口、Traceroute 等结果应提供摘要结论和逐项明细。
- 对失败节点/超时跳点显示“无响应/超时”，不要直接断言该设备离线。
- 扫描范围必须可见；默认采用最小必要范围，避免默认全网扫描。
- 对可能触发安全告警的扫描显示范围、并发、请求强度和停止方式；支持取消。
- 对外部目标执行扫描前，要求用户确认其具有授权；在产品提示中明确授权边界。

### 4.7 安全检测
- 将“资产/目标范围”“检测策略”“执行强度”“授权确认”“结果与证据”分区。
- 仅提供授权范围内的诊断与安全验证；不默认启用破坏性测试、持久化、隐蔽或数据破坏动作。
- 风险等级必须同时有文字标签与颜色；等级体系在全应用统一。
- 结果分为摘要、发现项、证据、影响、修复建议；证据应可追溯到任务与时间。
- 高风险动作必须二次确认，确认文案应描述具体目标与影响，不能只写“确定继续吗”。

### 4.8 任务、日志与报告
- 任务列表字段统一：任务名称、目标、类型、开始时间、耗时、状态、操作者/项目（若适用）。
- 状态建议：待运行、准备中、运行中、已完成、部分成功、失败、已取消；禁止用一个“处理中”覆盖所有状态。
- 日志支持级别过滤、文本搜索、时间排序、复制与导出；敏感字段在显示和导出时统一脱敏。
- 报告需区分结论、检查范围、方法、发现、证据、限制、建议；不能把原始日志直接当成专业报告。
- 任何导出动作应显示保存位置或复制结果反馈；失败时给出原因和重试路径。

## 5. 组件规范

### 5.1 按钮
- Primary：每个页面/对话框原则上只有一个最主要的提交动作。
- Secondary：常见辅助操作，如取消、导出、复制。
- Subtle/Ghost：工具栏次级动作。
- Danger：删除、停止服务、清空历史等高影响操作。
- 按钮文案使用明确动词：“开始检测”“发送请求”“保存配置”，避免“确定”“执行”这类缺少上下文的词。
- 所有按钮需有正常、悬停、按下、禁用、键盘焦点状态；异步操作需有忙碌状态。

### 5.2 输入框与表单
- 每个字段都有可见标签；不能只依靠 placeholder 表达字段名称。
- 占位符用于示例，不用于说明完整规则。
- 必填、可选、默认值、单位、格式要求明确。
- 错误提示贴近字段，并提供修正方向；不要只在页面顶部弹一句“参数错误”。
- 密码/API Key 使用安全输入控件；显示明文是用户主动操作。
- 输入验证应避免丢失用户输入；错误修正后及时更新提示。

### 5.3 表格与列表
- 适合多行同类数据；字段标题清楚，重要列靠左，数值/时间可按需对齐。
- 支持空状态、加载状态、失败状态；大数据列表使用虚拟化。
- 行操作不应只在悬停后才可发现；高频操作可放在行尾菜单。
- 不用整行红底表示普通失败；用状态标签、图标和局部强调。
- 表格应提供合理的列宽、截断提示和详情查看方式。

### 5.4 状态标签
全应用统一状态语义：
- 成功/健康：绿色 + 图标/文字
- 运行中：蓝色 + 进度/旋转图标 + 文字
- 警告/部分成功：琥珀色 + 文字
- 失败/危险：红色 + 文字
- 未知/未检测：中性色 + 文字
禁止仅靠颜色区分；不把“未检测”呈现为“失败”。

### 5.5 对话框、抽屉与通知
- 对话框只用于需要用户决策、确认或输入少量信息的场景；复杂流程用独立页面/向导。
- 标题应说明决策主题；正文描述影响；按钮顺序遵循 Windows 常见习惯。
- Toast 只反馈短暂、非阻断结果；错误若需要用户采取行动，应留在页面内。
- 不以连续弹窗展示诊断过程；过程信息放在任务面板。
- 关闭弹窗时若有未保存内容，提示用户保留/放弃。

### 5.6 空、加载、错误和成功状态
每个主要页面必须定义以下状态：
- 初始空状态：说明此处是什么、如何开始、提供主操作。
- 加载/准备状态：说明正在做什么；避免无限旋转且没有文字。
- 运行状态：显示阶段、耗时、停止入口。
- 成功状态：总结结果、提供下一步动作。
- 部分成功状态：明确成功与失败的部分。
- 错误状态：解释原因、可恢复性、重试或查看详情入口。
- 无权限/缺少依赖状态：说明缺什么、如何配置；不能伪装成普通失败。

## 6. 交互、可访问性与键盘

- 支持 Tab/Shift+Tab、Enter、Esc、方向键等符合控件语义的键盘操作。
- 焦点环清晰可见；不得移除系统焦点样式而不提供替代。
- 常见动作应有合理快捷键；快捷键在菜单/提示中可发现，不应冲突于编辑控件。
- 所有图标按钮必须有 ToolTip 和可访问名称；不能只提供图标而无语义。
- 文本与背景应满足可读对比；小字号辅助文本仍需可辨认。
- 不使用仅靠颜色、动画或声音传达的状态。
- 动画轻量且可中断；不为装饰添加持续运动。
- 长任务异步执行，UI 线程不得阻塞；关闭应用时对运行任务采用明确策略。
- 窗口缩放时，优先调整列宽/区域布局；不得遮挡主操作或将内容挤成不可读的窄列。

## 7. 主题与资源实现

- 统一使用 ResourceDictionary 管理颜色、间距、字号、圆角、边框、阴影、控件样式。
- 主题切换通过替换/合并资源字典实现，不在 ViewModel 或页面代码里到处写颜色判断。
- 业务页面禁止直接硬编码颜色、字号、Margin、CornerRadius；特殊情况必须有注释并复用令牌。
- 组件样式集中维护；优先复用基础控件样式，不复制粘贴出多个几乎相同的按钮/输入框样式。
- 避免大量 `UpdateSourceTrigger`、事件处理和业务逻辑混在 code-behind；遵循项目 MVVM 约定。
- 页面状态、任务状态与业务逻辑由 ViewModel/服务负责；View 负责呈现与用户输入。
- 若仓库已选用第三方 Fluent/WPF UI 库，先评估并复用，不要再引入第二套视觉体系；新增依赖需说明理由。
- 采用统一图标资源封装，图标大小、线宽、基线和对齐方式保持一致。

## 8. 文案与本地化

- 默认简体中文；协议字段、命令、错误码等技术名词保留必要英文。
- 句子短、动作明确、避免夸张营销话术。
- 日期时间、单位、数字格式统一；耗时使用毫秒/秒/分等清楚单位。
- 文案区分“功能未实现”“当前环境不可用”“检测失败”“用户取消”，不混为一谈。
- 所有用户可见文案集中管理，避免散落在代码里，方便未来本地化。

## 9. 数据安全与安全交互

- 密码、Token、Cookie、Authorization、API Key、完整带认证 URL 默认脱敏。
- 脱敏规则同时应用于日志、历史记录、剪贴板提示、报告和导出文件。
- 日志不应默认记录完整请求体中的敏感字段；提供必要时的显式查看与访问控制策略。
- 具有副作用的操作应明确说明目标、操作类型和影响范围。
- 扫描类工具默认最小范围、有限并发、可取消；授权确认必须可追溯到任务。
- 不能把未执行的安全检查显示为通过；不能以示例数据冒充真实检测结果。

## 10. WPF 工程实现约束

- 延续项目既定 C#/.NET/WPF/MVVM 架构；优先沿用现有导航、路由、依赖注入、日志与任务服务。
- 先检查仓库现状、现有依赖与已有控件，再决定如何实现；不要在未勘察时重写整个项目。
- 采用可复用的 View/Control：AppShell、NavigationItem、PageHeader、PrimaryButton、StatusBadge、EmptyState、LoadingState、ErrorPanel、TaskProgressPanel、ResultSummary、LogViewer 等。
- 对表格/日志/消息等大列表启用虚拟化；避免把大量日志一次性全部创建为视觉元素。
- 异步调用使用 async/await 与取消令牌；禁止在 UI 线程执行网络扫描、SDK 阻塞调用或长时间文件操作。
- 所有异步任务需定义取消、异常处理、状态更新与日志记录策略。
- 使用设计时数据辅助 UI 开发，但设计时数据与真实运行数据必须明确区分，生产模式不得误显示样例。
- 遵循现有命名和文件组织；如果仓库没有规范，建议按 `Views/`, `ViewModels/`, `Controls/`, `Themes/`, `Resources/`, `Services/` 分层。
- 先建立设计令牌和基础组件，再实现页面；不要每页独立设计。
- 不因 UI 优化而改写协议实现、诊断逻辑或安全边界；涉及业务逻辑时拆分提交并说明。

## 11. 推荐实施顺序

### 阶段 A：仓库勘察与基线
1. 阅读 README、PRD、架构、功能树、UI 线框和现有代码。
2. 确认 .NET/WPF 版本、目标框架、第三方 UI 库、导航方案、主题机制。
3. 输出当前 UI 结构、缺口、冲突与最小改造计划。
4. 未经批准不得大规模替换依赖或重建项目。

### 阶段 B：设计系统
1. 建立浅色/深色资源字典与设计令牌。
2. 建立字体、图标、间距、边框、按钮、输入框、状态标签等基础样式。
3. 建立应用壳层：标题栏、导航、页面容器、全局搜索/命令入口。
4. 验证缩放、主题切换、键盘焦点与高 DPI。

### 阶段 C：基础组件与工作台
1. 实现空/加载/错误/成功状态组件。
2. 实现任务状态、结果摘要、日志面板、通知和确认对话框。
3. 用真实服务状态或明确的空状态完成工作台，不伪造指标。
4. 形成可复用页面模板。

### 阶段 D：按模板改造业务页面
依照 PRD 与功能树优先级，逐页实现视频接入、IoT、网络诊断、API、安全检测、任务/报告等页面。每页必须包含参数校验、执行中、结果、错误和空状态。

### 阶段 E：一致性与验收
检查所有页面的布局、控件、状态、文案、键盘、主题、敏感信息遮蔽、窗口缩放与长任务体验。

## 12. UI 验收清单（Definition of Done）

### 视觉一致性
- [ ] 颜色、字号、间距、圆角、边框来自统一令牌。
- [ ] 主按钮层级明确；页面没有不必要的卡片堆叠。
- [ ] 图标体系一致；图标按钮有 ToolTip/可访问名称。
- [ ] 浅色/深色主题均可读，状态颜色含义一致。

### 直觉与交互
- [ ] 每页标题、用途、主要操作一目了然。
- [ ] 表单字段有标签、校验和就近错误说明。
- [ ] 执行中可见状态/耗时；可取消时能取消。
- [ ] 成功、部分成功、失败、取消和依赖缺失有不同表达。
- [ ] 页面切换不意外丢失上下文或中断任务。

### 工程质量
- [ ] UI 不阻塞；长列表虚拟化；异步任务可取消。
- [ ] View 与业务逻辑分离，遵循 MVVM。
- [ ] 主题与组件样式集中管理，没有大量硬编码视觉值。
- [ ] 无假数据冒充真实状态；设计时数据不进入生产展示。
- [ ] 运行日志与报告中敏感字段默认脱敏。

### 窗口与可访问性
- [ ] 1366×768 下核心流程可完成。
- [ ] 窗口缩放时关键按钮不会被裁切。
- [ ] 键盘焦点可见，Tab 顺序合理。
- [ ] 高 DPI 下文本、图标和边界没有模糊或错位。
